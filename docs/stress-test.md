# UtilityGuard: خطة الـ Stress Test والمراجعة الكاملة

آخر تحديث: 30 أكتوبر 2026. **الملف ده خطة بس. ماتنفّذش منه حاجة لسه.**
الهدف: نوصل لنقطة نقول فيها بثقة إن مفيش غلطة في أي حاجة، أو نكتب بالظبط إيه اللي لسه غلط ونعرف حجمه.

**القاعدة:** مفيش حاجة تتعدّ "شغالة" لأن الاختبار الآلي نجح. الشغال معناه إننا جرّبناه بأيدينا بالشروط الصعبة، وسجلنا الرقم اللي طلع، وقارنّاه بمعيار نجاح مكتوب قبل التجربة.

## 0. إزاي تستخدم الملف

1. كل بند له رقم (مثلاً `M-3`)، وخطوات التجربة، و**معيار النجاح مكتوب قبل التشغيل**. ماتغيّرش المعيار بعد ما تشوف النتيجة.
2. النتيجة بتتسجل في جدول القسم 15 (رقم البند، التاريخ، النتيجة الفعلية، ناجح/فاشل/ملاحظة، رابط لقطة شاشة أو ملف خرج).
3. أي بند فشل بيتحول لسطر في سجل المشاكل (القسم 14) مع خطورته، وبعد الإصلاح بنعيد **البند ده + كل اللي قبله في نفس القسم**.
4. بنود علامتها **[سكريبت]** محتاجة سكريبت مش موجود دلوقتي. لازم يتكتب في `backend/scripts/stress/` ويتحط في الريبو عشان يتعاد.
5. بنود علامتها **[فرضية]** هي حاجات شاكّين فيها ومش متأكدين. عادي جداً إنها تفشل، ده المطلوب إننا نعرف.

### الخطورة
| المستوى | معناه | يمنع العرض؟ |
| --- | --- | --- |
| S1 | رقم غلط بيظهر للمستخدم، أو قرار غلط، أو انهيار | آه |
| S2 | سلوك مضلل أو رقم مش متسق بين شاشتين، أو ميزة بتفشل في ظروف ممكنة قدام اللجنة | آه لو في مسار العرض |
| S3 | عيب شكل أو نص أو حالة نادرة | لأ، بس يتكتب |

### ظروف التشغيل (سجلها مع كل جولة)
- commit hash (`git rev-parse --short HEAD`) وإن الشجرة نضيفة.
- `LLM_OFFLINE=1` أو live (واسم الموديل)، و`SIM_SEED`، و`DISPATCH_SECONDS_PER_HOUR`.
- تاريخ ووقت الجهاز (بعض الأخطاء بتظهر في أيام معينة، زي ما حصل مع الجمعة).
- المتصفح وعرض الشاشة.

> **تحذير توكنز:** حد Groq المجاني 200 ألف token في اليوم. كل الحلقات المتكررة بـ `LLM_OFFLINE=1`. الجولات الـ live القليلة المقصودة بس (القسم 8 والقسم 12).

## 5. نموذج الخطر (Failure model) والإنذار المبكر

**حقيقة لازم تفضل مكتوبة:** نموذج الخطر متدرّب على hazard **اصطناعي** (من تصميمنا). الرقم ده ترتيب وليس احتمال معاير، ومش دقة ميدانية.

| ID | التجربة | معيار النجاح |
| --- | --- | --- |
| R-1 | **الرجوع للـ hazard:** هل النموذج بيسترجع الـ hazard اللي ولّد البيانات؟ AUC/ارتباط ترتيبي (Spearman) على بيانات اختبار منفصلة [سكريبت]. | رقم مكتوب. واضح أنه بيقيس "استرجاع الـ hazard" مش دقة الواقع |
| R-2 | **سلوك رتيب (monotonicity):** ثبّت كل الـ features وزوّد العمر، ساعات التشغيل، الانحراف عن الـ twin، التذبذب، الحمل، الحرارة واحدة واحدة [سكريبت]. | الخطر ما بيقلش مع زيادة أي عامل خطر |
| R-3 | المعايرة: هل الأرقام بين 0 و1 بتتوزع معقول؟ الـ UI بيقول "risk score" مش "احتمال" في كل مكان (Executive، Why، الإنذار، الـ PDF، الـ agents). | مفيش مكان بيكتب "probability" أو "% chance" |
| R-4 | الأهمية النسبية للـ features: هل الانحراف والتذبذب هما اللي بيحركوا الإنذار؟ | مفهوم ومكتوب |
| R-5 | **الإنذار المبكر على `scn-pump-wear`:** `minutesToFailure` = 3 و5 و8 و12 و20 × 3 طلمبات مختلفة × 3 seeds [سكريبت]. | في كل حالة: الإنذار قبل العطل، وlead time مسجل، ومفيش حالة من غير إنذار. توزيع الـ lead time مكتوب (live اتقاس 176 ث، اختبارات حوالي 4 دقايق) |
| R-6 | **الإنذارات الكاذبة:** كل الـ 15 سيناريو × 4 ساعات بداية × يوم عمل وجمعة وسبت [سكريبت]. ما عدا `scn-pump-wear`. | صفر إنذار كاذب |
| R-7 | **تشغيل طويل نضيف:** 24 ساعة محاكاة بلا سيناريو. | صفر إنذار |
